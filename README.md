# Explore With Me

Backend для публикации событий, подбора мероприятий, управления заявками и комментариями.

## Стек

- Java 21
- Spring Boot 3.3
- Spring Cloud Config, Netflix Eureka, Gateway, OpenFeign
- Resilience4j и Spring Retry
- Spring Data JPA
- PostgreSQL
- Apache Kafka, Avro, gRPC и Protobuf
- Maven
- Docker Compose

## Архитектура

Внешние запросы принимает Gateway на порту `8080`. Он сохраняет прежний REST API и направляет запросы в нужный сервис через Eureka.

Прикладная часть находится в `core`:

- `event-service` — события, категории и подборки;
- `request-service` — заявки на участие;
- `user-service` — пользователи;
- `comment-service` — комментарии;
- `common` — общие DTO внешнего и внутреннего API;
- `main-service` — точка запуска без бизнес-логики.

У каждого прикладного сервиса своя база PostgreSQL. Таблицы разных сервисов не связаны внешними ключами. Конфигурации находятся в `infra/config-server/src/main/resources/config`.

Инфраструктурные модули:

- `infra/discovery-server` — реестр Eureka;
- `infra/config-server` — централизованные настройки;
- `infra/gateway-server` — маршрутизация;
- `stats-service` — рекомендательная система.

Рекомендательная система состоит из трёх сервисов:

- `collector` принимает действия пользователей по gRPC и отправляет их в `stats.user-actions.v1`;
- `aggregator` обновляет сходство мероприятий и публикует его в `stats.events-similarity.v1`;
- `analyzer` сохраняет данные в PostgreSQL и предоставляет рекомендации по gRPC.

Схемы сообщений и сериализация Avro находятся в `stats-contracts`, gRPC-клиенты — в `stats-client`.
Collector и Analyzer используют случайные gRPC-порты, опубликованные в Eureka.

## Взаимодействие сервисов

Сервисы обращаются друг к другу через OpenFeign и имена из Eureka.

Внутренний API:

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/internal/users/{userId}` | получить пользователя |
| `POST` | `/internal/users` | получить пользователей одним пакетным запросом |
| `GET` | `/internal/events/{eventId}` | получить данные события для проверок |
| `POST` | `/internal/requests/counts` | получить количество подтверждённых заявок по списку событий |
| `GET` | `/internal/requests/users/{userId}/events/{eventId}/confirmed` | проверить подтверждённое участие |
| `POST` | `/internal/comments/counts` | получить количество опубликованных комментариев по списку событий |

Счётчики заявок и комментариев загружаются пакетно, поэтому количество межсервисных запросов не зависит от числа событий. Если сервис заявок или комментариев временно недоступен, сервис событий возвращает нулевые счётчики. Для повторных вызовов и защиты от сбоев используются Spring Retry и Resilience4j.

## Внешний API

Все внешние запросы отправляются через `http://localhost:8080`.

- [Основной API](ewm-main-service-spec.json)

Маршруты пользователей, заявок и комментариев сохраняются. В DTO событий поле `views` заменено на `rating` типа `double`.

Для `GET /events/{id}`, `GET /events/recommendations` и `PUT /events/{eventId}/like` нужен заголовок `X-EWM-USER-ID`.
Рекомендации принимают параметр `size` (по умолчанию 10). Успешный лайк возвращает `204`.
Список `GET /events` не отправляет просмотры; для сортировки по рейтингу используется `sort=RATING`.

Веса действий: просмотр — 0.4, регистрация — 0.8, лайк — 1.0. Для каждого пользователя и мероприятия
хранится максимальный вес, а рейтинг мероприятия равен сумме этих весов.
Сходство рассчитывается как сумма минимальных весов общих пользователей, делённая на квадратный корень
из произведения суммарных весов мероприятий. Предсказанная оценка — средневзвешенная оценка соседей.
Из рекомендаций исключаются все мероприятия, с которыми пользователь уже взаимодействовал.

Регистрация сохраняется вместе с заявкой в таблице `registration_outbox`. После подтверждения Collector
запись удаляется, при недоступности сервиса отправка повторяется. Повторные действия не увеличивают рейтинг.
Настройки размера недавней истории и числа соседей находятся в конфигурации Analyzer.

## Запуск

~~~bash
docker compose up --build
~~~

После запуска:

- Gateway: `http://localhost:8080`
- Eureka: `http://localhost:8761`

Базы данных доступны локально на портах:

- события — `6542`;
- пользователи — `6543`;
- заявки — `6544`;
- комментарии — `6545`;
- рекомендации — `6541`.

Kafka доступна с хоста по `localhost:9094`, внутри Docker — `kafka:29092`.
Топики создаются автоматически контейнером `kafka-init`.
У топика действий одна партиция: агрегатору необходима вся матрица для расчёта пар.
История Kafka сохраняется без ограничения срока; после перезапуска агрегатор восстанавливает состояние
из неё. База Analyzer и данные Kafka хранятся в Docker volumes.

## Проверка

~~~bash
mvn clean verify -P check
~~~

Коллекции Postman находятся в каталоге `postman`. Для основного сервиса и дополнительной функциональности нужно использовать Gateway на порту `8080`.
